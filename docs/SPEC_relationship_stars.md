## 0. 一句话

仅分析**本人账号**的公开互动数据，按指定时间区间统计我与各个账号之间双向交流的频次与质量，计算出 0–100 的评分、1–5 星的评级，并附带直观明了的分析解释。评分仅作为数据参考，不构成对任何人的主观评价。

界面标题固定叫 **「互动关系星级」**，标题下方固定展示免责声明：

> 这里只统计公开的回复、引用和点赞，私信、线下、别的平台都看不到。分数只是线索，不代表真实关系，也不代表对方好不好。

## 1. 目标和非目标

**目标**
1. 半自动采集：以自然浏览节奏浏览相关页面，被动记录双向回复、可获取的点赞及互关状态，完成去重后妥善保存在本地。
2. 多维度区间分析：支持最近 7 天、最近 30 天（**默认 30 天**，7 天数据样本往往不足）及自定义起止日期。每个账号均清晰拆解为「我对他」与「他对我」两组数据。
3. 评分、评星与文字解读：每项评分均可查看明细；若互动数据过少则明确标注「样本不足」，避免强行给出低星。
4. 私人标注：支持为账号添加本地私人备注与「朋友」标签，与量化评分并排展示（手动标注不影响算法评分）。

**非目标（明确不做）**
- 不分析第三方账号，仅分析本人账号（由 `--me` 指定）与他人的互动数据。
- 不制作任何公开排行榜，不生成带有攀比性质的「铁粉排行」图片。
- 不给任何用户打上「假粉」「僵尸粉」「互关党」等贬损标签。低分文案仅陈述客观数据事实（例如「这段时间互动很少」）。
- 不执行任何写操作：不自动点赞、不回复、不关注、不取关、不发私信、不拉黑。采集脚本与 AI 代理均严格保持只读。
- 不调用付费 X API，不使用账号 cookie/token 直接请求非官方 GraphQL 接口。
- 不向任何外部服务器上传数据，所有计算完全在本地完成。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 我 / me | 被分析的自己账号（例如 `me_demo`） |
| 对方 / account | 和我有互动的另一个账号 |
| out（我对他） | 我发起、指向对方的互动：我回复他、我引用他、我赞他 |
| in（他对我） | 对方发起、指向我的互动：他回复我、他引用我、他赞我 |
| 说话类互动 | `reply`、`quote`（v0.2 可选加 `mention`） |
| 问候 | 被第 7 节判为问候的说话类互动（早安、互关、浇水……） |
| 实质互动 | 说话类互动里不是问候的那些。双向性、往返只看实质互动 |
| 点赞 | `like`，只当辅助加分 |
| 对话 / thread | 同一个 `conversation_id` 下，我和这个账号之间的说话类互动 |
| 一轮 / round | 一条实质回复，它的 `in_reply_to_status_id` 指向本表里**对方方向**的一条实质互动（A 回了 B 的话之后，B 又接着回了 A 这一条）。只靠「同一对话里方向交替」不算，见 6.5 |
| 无法确认往返 | 回复缺 `in_reply_to_status_id`，或父推文没采集到，没法判断是不是在接对方的话 |
| 区间 | 分析的起止日期，含首尾两天，长度记为 $D$ 天 |

## 3. 数据来源和可得性

| 信号 | 方向 | 在哪儿拿 | 能不能拿到 | 备注 |
|---|---|---|---|---|
| 别人回复我的帖子 | in / reply | 我每条帖子的详情页（滚动加载回复）；或我已授权的 X 官方接口按 `conversation_id` 搜索 | 能 | 详情页里别人回复别人的楼中楼也会被抓到，入库时只留 `in_reply_to_user == me` 的 |
| 我回复别人 | out / reply | 我自己的 `x.com/<me>/with_replies` 页面 | 能 | 这个页面加载多、容易触发限速，单独限速（第 4 节） |
| 引用 | in / out quote | 我的帖子的「引用」页；我自己的主页 | 能（被动捕获时） | v0.1 可以先不做，字段先留着 |
| 他赞我 | in / like | 我的帖子的 `/likes` 页面（只有作者本人能看到完整列表，**待核实**）；或官方接口 `GET /2/tweets/:id/liking_users` | 谁赞了能拿到；**什么时候赞的拿不到** | 我们实测查自己帖子的 `liking_users` 时没扣费，只是一次观察，以开发者后台为准。时间问题见 5.4 |
| 我赞他 | out / like | 我自己的 `x.com/<me>/likes` 页面；或官方接口 `GET /2/users/:id/liked_tweets` | 赞了哪些帖子能拿到；**什么时候赞的拿不到** | 页面顺序大致按点赞时间，但没有时间字段（**待核实**），见 5.4 |
| 别人赞了谁 | — | — | 拿不到 | 我们观察到 2024 年起 X 把点赞列表改成仅本人可见，别人的点赞页看不到（**待核实**具体范围） |
| 互关状态 | 快照 | `following` / `followers`（或 `verified_followers`）导出 | 能 | 只做快照对比，不参与打分（见 6.6） |
| 私信、Space、线下 | — | — | 不采集 | 免责声明里写明 |

## 4. 采集方案

### 4.1 被动捕获：twitter-web-exporter（首选）

- 用户在自己的浏览器里装 Tampermonkey + [twitter-web-exporter](https://github.com/prinsss/twitter-web-exporter)。它拦截页面本来就会加载的 GraphQL 响应，**只记录我滚过的内容**，不额外发请求。
- 要打开的页面：
  1. 我最近 N 条帖子（区间内发的）的详情页，各滚到底 → 回复（in）
  2. `x.com/<me>/with_replies` 滚到区间起点 → 我的回复（out）
  3. 我的帖子的 `/likes` 页 → 他赞我（in like）
  4. `x.com/<me>/likes` 滚一段 → 我赞他（out like）
  5. 每月一次 `following` / `followers` → 互关快照
- 每类页面在脚本面板里分开导出（JSON），导出后清空已捕获数据，避免混在一起。具体哪个页面对应脚本里哪个模块（例如 `with_replies` 归在哪个模块），以它的 README 为准（**待核实**）。
- 转换：在 `adapters/twitter_web_exporter.py` 里加一个子命令 `interactions`，把导出 JSON 转成第 5 节的 `interactions.csv`（规则见 5.2）。

### 4.2 可选：AI 电脑代理帮忙滚动

ChatGPT / Codex Computer Use、Claude in Chrome、Grok 等代理**只负责滚动和翻页**，捕获仍然由 twitter-web-exporter 完成。安全限制（必须写进给代理的提示词里）：

| 规则 | 默认值（**待验证**） |
|---|---|
| 只读：不点赞、不回复、不关注、不点任何弹窗里的确认按钮 | 硬规则 |
| 每次滚动后随机停顿 | 2–6 秒均匀随机；每 20 屏额外停 30–90 秒 |
| 每次会话最多打开的页面数 | 帖子详情页 ≤ 30 个；`/likes` ≤ 10 个 |
| `with_replies` 单独限速 | 每次会话最多滚 60 屏，同一天最多 1 次会话 |
| 每次会话总时长 | ≤ 30 分钟 |
| 立即停止的情况 | 出现验证码、「请求过多/Rate limit exceeded」「稍后再试」、要求重新登录、账号警告、页面一直空白；停下后报告停在哪一页，**不重试** |
| 会话之间 | 至少间隔 2 小时 |

提示词模板放在 `docs/data-collection-options.md`，这里新增的页面清单按上表补进去。

### 4.3 风险提示

- 被动捕获只记录正常浏览加载的内容，风险较低，但**大量、快速、机械地滚动**本身就可能触发限速或风控，所以有上面的限制。
- 可选的自动读取会在浏览器里读 `ct0`，并可能使用 X 网页公开令牌，只为请求自己的名单。不把令牌或 cookie 存下来，也不调用写接口。不用无头浏览器批量跑。
- X 的服务条款禁止未经许可的自动化抓取（爬取）。AI 代理代替人滚动属于灰色地带，用户自己判断、自己承担；文档里要原样写出这句话。

### 4.4 油猴版里的可选自动读取

默认仍是自己往下翻。面板里的「自动读取」默认关闭，开启前要勾选确认。

自动读取默认关闭。开启后脚本自己请求正在关注（默认只读这一份，用 `followed_by` 判断对方是否关注我；也可以同时读关注者和认证粉丝）。游标翻页，每页大约 100 人，中间不再故意等待，单次最多 120 页。已经记过的一页只要游标还在往下就继续。停止只看这一轮新建的去重人数，不用本机已经存过的人数。没有下一页、空页、游标不变、本轮人数达到公开总数，或单次 120 页，才结束这一份名单。进度写「读取中 本轮已读 N / 共约 M」，结束时写本轮读了多少人、多少页。接口编号优先用页面刚才的请求，否则从已加载的页面代码里查找 `queryId` 和 `operationName`；400 或 404 时再找一次。登录状态优先用刚才的请求；没有时用 X 网页公开的令牌，并在浏览器里读 `ct0`，只写成发往 x.com 的 `x-csrf-token`。令牌和 cookie 不写入备份或诊断。遇到 429、其他非成功状态码、`x-rate-limit-remaining` 小于等于 2，马上停并不自动重试。读不成就请用户自己打开名单页往下翻，被动钩子仍会记下页面加载的内容。这是自动化抓取，不能保证安全。刷新页面后回到关闭。

只读正在关注时，互关和没回关只包括你关注的人。你没关注、但对方关注了你的人不会出现。命令行在 `following.csv` 带 `followed_by` 列时用同一规则修正粉丝侧；没有这一列时仍要两份名单。

## 5. 数据模型

v0.1 用 CSV（方便手改和检查）；v0.3 可以换成 SQLite，表结构相同。所有时间存 UTC 的 ISO 8601，显示时转成用户时区。

### 5.1 表结构

**accounts.csv**

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | str | X 数字 ID，能拿到就用它做主键 |
| handle | str | 用户名，小写，不带 @ |
| name | str | 显示名 |
| first_seen | datetime | 第一次出现在数据里 |
| last_seen | datetime | 最近一次 |

**interactions.csv**（核心表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | str | 主键，规则见 5.3 |
| tweet_id | str | 回复/引用本身的推文 ID，**每条回复必须唯一**；点赞为空 |
| ts | datetime | 互动发生时间。回复/引用 = 推文 `created_at`；**点赞一律为空**（拿不到点赞时间，见 5.4） |
| account | str | 对方 handle（或 user_id） |
| direction | enum | `out`（我对他）/ `in`（他对我） |
| type | enum | `reply` / `quote` / `like`（v0.2 加 `mention`） |
| post_id | str | 回复/引用时等于 tweet_id；点赞时是被赞帖子的 ID |
| conversation_id | str | 所属对话 ID；点赞时等于被赞帖子的 conversation_id，拿不到就用 post_id |
| in_reply_to_status_id | str | 被回复推文的 ID。回复必须有，缺了就标「无法确认往返」 |
| parent_kind | enum | 父推文**不在本表**时由适配器填写：`root`（父推文是对话起点帖）/ `other`（父推文采集到了，但不是我和对方之间的互动，即别的分支）/ `unknown`（没采集到）。父推文在本表里时留空，评分程序自己查 |
| text | str | 回复/引用正文；点赞为空 |
| is_greeting | bool | 问候判定结果（第 7 节），入库时算好，规则变了可以重算 |
| post_created_at | datetime | 点赞专用：被赞帖子的发布时间（点赞一定发生在它之后） |
| first_observed_at | datetime | 点赞专用：我们的采集**第一次**看到这个赞的时间（点赞一定发生在它之前） |
| observed_baseline | bool | 点赞专用：这个赞是在**第一次**采集该列表时就已经存在的（旧赞），不能当成「最近发生」 |
| source_file | str | 来自哪个导出文件，方便追查 |
| captured_at | datetime | 这一行的捕获时间 |

**mutual_snapshots.csv**

| 字段 | 说明 |
|---|---|
| snapshot_date | 快照日期 |
| account | 对方 |
| i_follow | 我是否关注他 |
| follows_me | 他是否关注我（如果只有 verified_followers 列表，要在 `source` 里注明，未认证粉丝会漏） |
| source | 用的哪份名单 |

**notes.csv**（只在本地，永远不进仓库和导出）

| 字段 | 说明 |
|---|---|
| account | 对方 |
| is_friend | 手动「朋友」标签，true/false |
| note | 私人备注 |
| updated_at | 修改时间 |

### 5.2 从导出推文生成 interactions 的规则

对每条推文（作者记为 `author`，我记为 `me`）：

0. 每条推文都要带上自己的 `tweet_id`、`conversation_id`、`in_reply_to_status_id`（GraphQL 里一般叫 `rest_id`、`conversation_id_str`、`in_reply_to_status_id_str`，**待核实**）。
1. `author == me` 且 `in_reply_to_user` 存在且 `!= me` → `out/reply`，`account = in_reply_to_user`。
2. `author != me` 且 `in_reply_to_user == me` → `in/reply`，`account = author`。
3. `author == me` 且引用了别人的推文 → `out/quote`，`account = 被引用作者`；`author != me` 且引用了我的推文 → `in/quote`。
4. 我回复自己（串推）、别人之间的楼中楼、转推：**丢弃**。
5. 点赞：我帖子的点赞者列表里每个人 → `in/like`；我的 `/likes` 页里每条帖子 → `out/like`，`account = 帖子作者`。
6. 排除列表（配置项，默认 `grok`）里的账号丢弃。
7. 填 `parent_kind`：父推文 ID == `conversation_id` → `root`；父推文在同一批导出里、但不是我和这个账号之间的互动 → `other`；父推文不在导出里 → `unknown`；父推文就在 interactions 里 → 留空。
8. 点赞：`post_created_at` 填被赞帖子的 `created_at`；`first_observed_at` 填这次导出的时间，**以后再导出时不覆盖**（保留最早一次）；如果这是这个列表的第一次采集，`observed_baseline = true`。

### 5.3 去重规则和校验

| 类型 | id 规则 | 重复时 |
|---|---|---|
| reply / quote | `tw:<tweet_id>` | 内容相同 → 合并；内容不同 → 保留第一条并报警 |
| in like | `like:in:<点赞者>:<我的帖子ID>` | 合并，`first_observed_at` 取最早，`observed_baseline` 取最早那次的值 |
| out like | `like:out:<帖子作者>:<帖子ID>` | 同上 |

- 同一份数据多次导入，结果必须完全一样（幂等）。
- handle 统一小写；能拿到 user_id 时以 user_id 为准合并（对方改过名也不会算成两个人）。
- 推文被删：已入库的保留，加 `deleted=true` 的可选字段，不影响打分。

**导入前校验（v0.1 必做，结果打印成警告，不中断）：**

| 检查 | 警告文案示例 |
|---|---|
| 同一 `tweet_id` 出现多次、内容相同 | 重复 tweet_id N 条（内容相同，已合并） |
| 同一 `tweet_id` 出现多次、内容不同 | tweet_id 重复且内容不同（保留第一条）：tw:… |
| 回复缺 `tweet_id` | 回复缺少 tweet_id：…（这一行丢弃） |
| 多条回复共用同一个 `post_id` | N 个 post_id 被多条回复共用，检查是不是把 conversation_id 写进了 post_id |
| 回复缺 `in_reply_to_status_id` | N 条回复缺少 in_reply_to_status_id，这些回复无法确认往返 |
| 点赞缺 `post_created_at` 或 `first_observed_at` | N 个点赞时间信息不全，严格模式下不计分 |

### 5.4 点赞时间

X 的点赞数据里**没有「什么时候点的赞」**。官方 likes lookup 快速入门（<https://github.com/xdevplatform/docs/blob/main/x-api/posts/likes/quickstart/likes-lookup.mdx>，访问于 2026-10-19）里有两个接口：

- `GET /2/tweets/:id/liking_users`：返回的是**用户对象**，示例里请求了 `user.fields=created_at`，SDK 示例把它打印成 `Joined: {user.created_at}`，也就是**账号注册时间**；
- `GET /2/users/:id/liked_tweets`：返回的是**帖子对象**，`tweet.fields=created_at` 是**帖子发布时间**。

两个响应示例里都没有点赞事件本身的时间字段。所以：

1. **不能**把被赞帖子的 `created_at` 当成点赞时间（今天赞了一条一年前的帖子，会被错算到一年前，掉出最近 30 天）。
2. 只存两个确定的边界：$t_{post} = $ `post_created_at`（点赞一定在它之后）和 $t_{obs} = $ `first_observed_at`（点赞一定在它之前）。
3. **严格模式（默认）**：只有整个区间 $[t_{post}, t_{obs}]$ 都落在分析区间 $[s, e]$ 内时，这个赞才算「区间内」，参与打分。例如帖子 10 月 1 日发、10 月 19 日采集时看到的赞，一定发生在最近 30 天里。其余的赞（旧帖被赞、采集间隔太长）**在详细视图里显示为「时间不确定的点赞 N 次」，不计分**。
4. **按观察时间模式（可选，`--like-time observed`）**：用 $t_{obs}$ 当点赞时间，`observed_baseline = true` 的不算。界面和输出里必须明确写「点赞时间是按我们第一次看到的时间推断的」。只有定期采集（比如每周一次）时这个模式才有意义。

## 6. 打分

下面所有参数都放在配置文件 `relationship_config.json` 里，默认值都是**待验证**。

### 6.1 输入和预处理

对一个账号、一个区间 $[s, e]$（含首尾，$D = e - s + 1$ 天，周数 $K = \lceil D/7 \rceil$，周从 $s$ 开始每 7 天切一段）。

若所选区间内每天均有数据记录，则直接按日历天数 $D$ 计算。如果部分日期既无当天的采集文件，也无任何互动时间或点赞首次观察记录，这些日期将被认定为**无数据**而非零互动：它们不计入 $D$，也不算作没有交流的空闲日期。此时 $D$ 会自动校正为实际存在数据的有效天数，将这些有效日期按时序衔接后，再每 7 天划分为一周。单目录模式 `audit.py --data`、每日模式 `--data-root` 以及油猴版均遵循同一规则。14.1 中的用例由于每天均有记录，$D$ 仍为 30，期望分数不受影响。

- 说话类互动取 `ts` 在区间内的；点赞按 5.4 的规则判断在不在区间内。
- 说话类互动分成两组：**实质互动**（不是问候）和**问候**。
- 记号：
  - $n_{raw}$ = 说话类互动原始条数（含问候），$n_g$ = 问候条数；
  - $O$、$I$ = 我对他、他对我的**实质互动**条数（不加权，问候不算）；
  - $\mathcal{D}_{sub}$ = 有实质互动的日期集合；$\mathcal{D}_{g}$ = 只有问候、没有实质互动的日期集合（**按天去重**，一天发 5 句早安也只算 1 个问候日）；
  - $L_{in}$、$L_{out}$ = 区间内的点赞数。

### 6.2 样本不足（先判断，判断成立就不打分）

$$
n_{raw} < N_{min} = 3 \quad \text{或} \quad d_{raw} < M_{min} = 2
$$

$d_{raw}$ 是有说话类互动（含问候）的不同日期数。成立时显示「样本不足」，不给星，但明细照样展示。只有点赞没有说话的账号也是样本不足（解释里写「只有点赞」）。

> 用原始条数（含问候）判断：问候刷屏的账号条数不少，应该被打出低分让用户看到，而不是藏在「样本不足」里。

### 6.3 持续性 $P$（权重 40%）

问候日单独封顶：每个问候日只算 $g = 0.2$ 天，所有问候日加起来最多算 $C_g = 1$ 天。

$$
\tilde d = |\mathcal{D}_{sub}| + \min\big(C_g,\ g\,|\mathcal{D}_{g}|\big), \qquad
P_{day} = \min\left(1,\ \frac{\tilde d}{\alpha D}\right), \quad \alpha = 0.3
$$

即实质互动天数达到区间的 30%（30 天里 9 天）就记满；纯问候最多只能贡献 $1/(\alpha D)$（30 天时约 0.11）。

按周：**一周内至少有 1 条实质互动**才算活跃周，问候不算。

$$
P_{week} = \frac{\#\{k : \text{第 } k \text{ 周有实质互动}\}}{K}
$$

$$
P = \tfrac12 P_{day} + \tfrac12 P_{week}
$$

（备选：以后要支持 90 天以上的长区间，把 $P_{day}$ 换成对数缩放 $\min\big(1, \ln(1+\tilde d)/\ln(1+\alpha D)\big)$，v0.1 不做。）

### 6.4 双向性 $B$（权重 35%）：只看实质互动

$$
B = \begin{cases} \dfrac{\min(O, I)}{\max(O, I)} & O \ge 1 \text{ 且 } I \ge 1 \\[4pt] 0 & \text{否则} \end{cases}
$$

双方互发早安时 $O = I = 0$，$B = 0$。

### 6.5 对话往返 $R$（权重 25%）：只用严格回复链

对每条**实质**回复 $x$，看它的父推文 $p = $ `in_reply_to_status_id`：

| 情况 | 结果 |
|---|---|
| $p$ 在本表里，是**对方方向**的**实质**互动 | **算一轮** |
| $p$ 在本表里，但是问候 | 不算（接一句早安不算往返） |
| $p$ 不在本表里，`parent_kind = root` | 对话的开头，不算，也不报警 |
| $p$ 不在本表里，`parent_kind = other` | 别的分支，不算，详细视图计入「分支」 |
| $p$ 为空，或 `parent_kind = unknown` | **无法确认往返**，不算，详细视图计数 |

$$
\text{rounds} = \#\{x \text{ 算一轮}\}, \qquad
T = \text{有实质互动的对话数（按 conversation\_id）}
$$

$$
R = \begin{cases} \min\left(1,\ \dfrac{\text{rounds}}{\max(2T,\ 4)}\right) & T \ge 1 \\[4pt] 0 & T = 0 \end{cases}
$$

意思是：平均每个对话真的接上 2 次话、且总共至少 4 轮，才记满。

**严格回复链是唯一的计分方式。** 同一 `conversation_id` 里方向交替出现，不一定是在对话：可能是两个人在同一个帖子下各自回复不同的人（不同分支）。旧的「宽松模式」（同一对话里方向切换就算一轮）只作为详细视图里的一行提示：「同一对话里方向切换 N 次（未核实回复链，不计分）」。

### 6.6 点赞加分和互关

$$
\text{bonus} = \min\big(C_L,\ \beta\,(L_{in} + L_{out}),\ S_{base}\big), \quad \beta = 0.5,\ C_L = 5
$$

- 只算区间内的赞（5.4 严格模式），最多加 5 分，而且**不超过 $S_{base}$ 本身**：点赞最多让分数翻倍，不能把一个几乎没说过话的人抬上去。
- 互关状态**不参与打分**，只在表格里显示一列（✔ 互关 / → 我单向关注 / ← 他单向关注 / 空）。原因：互关本身就是「互关党」最容易刷的指标。**待验证**：校准后如果发现互关和朋友标签高度相关，再考虑加一个 ≤3 分的小加分。

### 6.7 总分、问候上限和星级

$$
S_{base} = 100\,\big(0.40\,P + 0.35\,B + 0.25\,R\big), \qquad
S_0 = \min\big(100,\ S_{base} + \text{bonus}\big)
$$

**问候上限**：问候占比 $n_g / n_{raw} \ge 0.8$ 时，最多 2 星，解释里写「主要为问候互动」：

$$
S = \begin{cases} \min(S_0,\ 39.9) & n_g / n_{raw} \ge 0.8 \\ S_0 & \text{否则} \end{cases}
$$

| 分数 $S$ | 星级 |
|---|---|
| ≥ 80 | ★★★★★ |
| 60–79.9 | ★★★★☆ |
| 40–59.9 | ★★★☆☆ |
| 20–39.9 | ★★☆☆☆ |
| < 20 | ★☆☆☆☆ |
| 样本不足 | 「样本不足」，不显示星 |

分数保留 1 位小数，星级用未四舍五入的分数判断。

> 已知取舍（**待验证**）：一个人每天跟我说早安、这个月另外只认真聊过 2 次，问候占比约 88%，会被压到最多 2 星（14.4 的「问候上限生效」用例，70.6 → 39.9）。校准时如果用户觉得这类人应该更高，就把 0.8 调高或改成按问候日占比算。

### 6.8 趋势

和**紧挨着的上一个等长区间**比（当前 $[s,e]$，上一个 $[s-D,\ s-1]$）：

| 情况 | 显示 |
|---|---|
| 两边都有分，$\Delta = S_{now} - S_{prev} \ge 10$ | ↑ +Δ |
| $\Delta \le -10$ | ↓ Δ |
| $|\Delta| < 10$ | → 持平 |
| 上一区间样本不足，这一区间有分 | 新出现 |
| 上一区间有分，这一区间样本不足 | 变少了 |
| 两边都样本不足 | — |

阈值 10 分**待验证**。

### 6.9 参数汇总（`relationship_config.json` 默认值，全部**待验证**）

| 参数 | 默认 | 含义 |
|---|---|---|
| `w_P, w_B, w_R` | 0.40, 0.35, 0.25 | 三个维度权重 |
| `alpha` | 0.3 | 活跃天数满分比例 |
| `greet_day` / `greet_day_cap` | 0.2 / 1.0 | 每个问候日折算天数 / 问候日合计上限 |
| `greet_share_cap` / `greet_max_score` | 0.8 / 39.9 | 问候占比阈值 / 触发后最高分 |
| `like_pts` / `like_cap` | 0.5 / 5 | 每个赞加分 / 点赞加分上限（另受 $S_{base}$ 限制） |
| `min_raw` / `min_days` | 3 / 2 | 样本不足阈值 |
| `like_time` | strict | 点赞计时：strict / observed |
| `trend_delta` | 10 | 趋势阈值 |

### 6.10 分层（金牌 / 银牌 / 单向）

分数与星级评定仍按上述公式计算。用户分层属于另一维度的规则判断，当前设定为待校准的初始门槛：

- **金牌与银牌均要求对方至少回复过 1 条推文**（原始回复，问候类回复也计入）。金牌的进阶门槛还包括：综合得分 ≥55、确认往返 ≥3 轮、双方各自实质回复 ≥3 条、问候占比低于 0.5，且实质互动天数 ≥2 天。
- **银牌**额外要求至少有 1 次确认往返。在此基础上，综合得分 ≥40 或确认往返 ≥2 轮，且未达到金牌标准，方可评为银牌。
- **若对方回复数为 0，或确认往返数为 0，均不能进入银牌。** 其中，当对方回复数为 0 且我方发出的原始条数 ≥3 时，无论总分是否达到 40 分，均优先归入「单向·我常去他没回」。
- 若对方确实回复过，但由于回复链未能匹配导致确认往返为 0，则不进入银牌，亦不会标记为「他没回」，通常会落入「其他有分」层级。

## 7. 问候识别

配置文件 `greetings.txt`（一行一个，可以自己加），默认：

```
早安 早上好 午安 晚安 互关 回关 互粉 浇水 浇朋友 浇浇 打卡 来了 你好 新朋友 gm gn follow back
```

判定（`is_greeting`）：

1. 去掉 @提及、链接；
2. 再去掉空白、标点、表情，剩下的叫 `core`；
3. `core` 为空（只有表情/标点）→ 是问候；
4. `len(core) <= 15` 且原文（不区分大小写）包含任一关键词 → 是问候；
5. 否则不是。

长度阈值 15 **待验证**。英文关键词（如 gm、gn 等）必须按照单词边界进行匹配，防止将 `gmail` 等词汇误判。「你好」「来了」等词汇在简短的正经提问中也可能出现（例如「你好，开源吗」），可能会被误判为问候；这是已知的规则权衡，用户可根据需要从词表中移除。长回复中顺带提及的「早安」不会被算作问候（第 4 条的长度阈值正是为此设计）。问候判定不会删除任何数据，明细列表中依然会保留并标注「问候」；但问候互动**不计入**双向性与往返轮数，在持续性得分中亦受到问候日上限的严格封顶（参见 6.3）。

实测误判案例：例如「正常，很多是互关来的」（共 11 字，且包含「互关」）会被判定为问候。此前在生成示例数据时便遇到过该情况，因此在示例中微调了用词；在后续版本中，计划在详细视图中允许用户手动将特定记录标记为「非问候」（v0.3）。

## 8. 解释文本模板

每个账号一段，按下面模板拼，没有的项省略：

```
@{handle}  {星级或「样本不足」}  {分数}  {趋势}
区间：{start} ~ {end}（{D} 天）
我对他：回复 {out_reply} 条、引用 {out_quote} 条、点赞 {L_out} 次
他对我：回复 {in_reply} 条、引用 {in_quote} 条、点赞 {L_in} 次
活跃 {d_raw} 天（实质互动 {d_sub} 天）、{active_weeks}/{K} 周；对话 {T} 个，确认往返 {rounds} 轮
问候类 {greet} 条（不计入双向性和往返）
无法确认往返 {unconfirmed} 条；分支 {branch} 条；同一对话里方向切换 {loose} 次（未核实回复链，不计分）
时间不确定的点赞 {likes_unscored} 次（不计分）
主要原因：{reasons}
互关：{mutual}    朋友标签：{is_friend}    备注：{note}
```

`reasons` 从下面规则里挑最多 2 条（按顺序判断）：

| 条件 | 文案 |
|---|---|
| 样本不足且只有点赞 | 这段时间只有点赞，没有说话类互动 |
| 样本不足 | 互动太少，先不打分 |
| 问候占比 ≥ 80%（触发问候上限） | 主要为问候互动 |
| 无法确认往返 + 分支 ≥ 实质回复的一半 | 有不少回复没法确认是在接对方的话 |
| $B = 0$ 且 $O > I$ | 主要是我在回复对方 |
| $B = 0$ 且 $I > O$ | 主要是对方在回复我 |
| $B < 0.3$ | 互动比较单向 |
| $R \ge 0.8$ | 有多轮真正接上的对话 |
| $P \ge 0.7$ | 互动分布在很多天 |
| $R < 0.2$ 且 $T \ge 3$ | 多是单句评论，很少接着聊 |

文案只描述事实，不出现「假粉」「僵尸」「不真诚」之类的词。

## 11. 校准计划

1. 用户从最近 30 天里挑约 10 个**心里确定是朋友**的账号，打 `is_friend=true`；再挑约 10 个**确定只是点头之交**的，打 `false`（这一列只用于校准，校准完可以清掉）。
2. 跑一遍打分，计算：
   - Spearman 等级相关 $\rho$（朋友=1、非朋友=0 和分数之间）；
   - 前 10 名里朋友的占比（precision@10）。
3. 网格搜索权重：$w_P, w_B, w_R$ 以 0.05 为步长，和为 1，每个在 0.15–0.6 之间；同时试 $g \in \{0.1, 0.2, 0.3\}$、$\alpha \in \{0.2, 0.3, 0.4\}$、问候上限阈值 $\in \{0.7, 0.8, 0.9\}$。
4. 只有当新权重让 $\rho$ 至少提高 0.1 时才换，避免对 20 个人过拟合；换了就在配置文件里记一行「改了什么、为什么、日期」。
5. 一个月后用新的区间再验证一次。
6. 校准结果只写在本地，不进仓库。

## 14. 测试用例（虚构数据）

示例数据：`examples/relationship/interactions.csv`（由 `make_relationship_example.py` 生成，533 行，其中 1 行是故意重复的同一 tweet_id，去重后 532 行）。每条回复都有唯一的 `tweet_id`，用 `in_reply_to_status_id` 连成回复链。`examples/relationship/reference_score.py` 是按本文公式写的最小参考实现，**只用来核对期望值**，正式实现不要求照抄它的结构。

### 14.4 单元测试（不依赖示例文件）

| 测试 | 输入 | 期望 |
|---|---|---|
| 问候：纯表情 | `☀️☀️` | 是问候 |
| 问候：短句含关键词 | `早安呀 @me_demo` | 是问候 |
| 问候：长句顺带关键词 | `早安，昨天你说的那个本地模型我试了，速度确实慢不少` | 不是问候 |
| 问候：英文大小写 | `GM!` | 是问候 |
| 问候：英文单词边界 | `gmail 登不上了` | 不是问候 |
| 问候：已知误判 | `正常，很多是互关来的` | 是问候（记录在案的误判，第 7 节） |
| 问候日去重 | 同一天 5 句早安 | 只算 1 个问候日 |
| 问候不撑持续性 | 30 天每天都只有问候 | $P_{day} = 1/9$，$P_{week} = 0$ |
| 问候上限生效 | 2 个对话各 1 轮真实往返（4 条实质）+ 30 天每天 1 句早安（双方轮流） | 问候占比 0.88；$S_{base}=70.6$ → $S=39.9$ ★2，「主要为问候互动」 |
| 往返：真实回复链 | in(回我原帖) → out(回这条 in) → in(回这条 out) | 往返 2 轮 |
| 往返：接问候不算 | out「早安」→ in(回这句早安，实质内容) → out(回这条 in) | 往返 1 轮（只有最后一条算） |
| 往返：分支 | 同一对话 out、in 交替，但父推文都是 `parent_kind=other` | 往返 0，分支计数 = 条数，宽松提示显示切换次数 |
| 往返：缺父推文 | `in_reply_to_status_id` 为空 | 往返 0，无法确认 +1，校验警告 |
| 双向性：问候不算 | 我 5 条实质，他 10 句早安 | $I=0$，$B=0$ |
| 点赞：严格区间 | 帖子 10-01 发、10-19 观察到，区间 9-20~10-19 | 计入 |
| 点赞：旧帖 | 帖子 2025-03-15 发、10-18 观察到 | 严格模式不计入，显示「时间不确定」；observed 模式计入 |
| 点赞：基线 | 第一次采集就看到的赞，`observed_baseline=true` | observed 模式不计入 |
| 点赞加分封顶 | $S_{base}=50$，区间内赞 30 次 | $S=55$ |
| 点赞不超过基础分 | $S_{base}=2.2$，赞 10 次 | 加分 2.2，$S=4.4$ |
| 总分封顶 | $S_{base}=98$，加分 5 | $S=100$ |
| 星级边界 | $S=79.95$ | ★4（用未四舍五入的值判断） |
| 校验：重复 tweet_id 内容不同 | 同一 tweet_id 两行，text 不同 | 保留第一条，警告「内容不同」 |
| 校验：共用 post_id | 4 条回复的 post_id 相同 | 警告「检查是不是把 conversation_id 写进了 post_id」 |
| 方向判定 | 我回复我自己的串推 | 丢弃 |
| 方向判定 | 别人在我帖子下回复别人 | 丢弃 |
| 排除账号 | `grok` 回复我 | 丢弃 |
| 区间边界 | ts 恰好是区间首日 00:00（用户时区） | 计入 |
| 时区 | ts 为 UTC `2026-09-19T08:00:00Z`，用户在 UTC-7 | 用户本地是 9-19 01:00，**不**计入 9-20 起的区间 |

> 注：参考实现为了简单按 naive 时间比较，正式实现必须先把 UTC 转成用户时区再切日期和周（最后两条测试）。用户时区由 `--tz`、配置里的 `timezone` 或系统本地时区决定，不写死某一个城市。

### v0.2（2026-10-19）：根据用户审阅修了 4 个问题

这 4 个问题都是用户自己审规格时找出来的，每个都先用 v0.1 的参考实现复现过，再改。

| # | 用户发现的问题 | 复现结果（v0.1 公式） | 改法 | 改后 |
|---|---|---|---|---|
| 1 | **纯问候能拿 5 星。** 问候权重 0.2 会累加，每天几句就把持续性和双向性填满 | 30 天双方每天各 5 句早安 + 10 个赞 → 80.0 ★5；只有他单向每天 5 句 → 45.0 ★3 | 问候按天去重、问候日合计最多折算 1 天；活跃周只认实质互动；双向性、往返只看实质互动；点赞加分不超过基础分；问候占比 ≥80% 最多 2 星，写「主要为问候互动」 | 两例都是 4.4 ★1（14.1 的 user_101、user_102） |
| 2 | **点赞时间用错了。** 用被赞帖子的 `created_at` 当点赞时间，今天赞一条一年前的帖子会掉出 30 天 | 确认：官方 likes lookup 快速入门里，`liking_users` 的 `created_at` 是用户对象的注册时间，`liked_tweets` 的 `created_at` 是帖子发布时间，都不是点赞时间 | 分开存 `post_created_at` 和 `first_observed_at`；严格模式只计入时间区间能确定的赞，其余在详细视图里显示不计分；可选「按观察时间」模式并明确标注 | 5.4；14.1 的 user_108 |
| 3 | **同一对话里方向交替不等于往返。** 可能是不同分支 | 分支用例在宽松模式下 61.2 ★4 | 严格回复链（`in_reply_to_status_id` 必须指向对方那条实质互动）是唯一计分方式；缺链标「无法确认往返」不计分；宽松切换次数只作提示 | 42.4 ★3（14.1 的 user_107） |
| 4 | **测试数据不守自己的去重规则。** 5 星示例的 16 条回复只用了 4 个 post_id，按 tweet_id 去重后只剩 4 条 | 复现：按 `tw:<post_id>` 去重后 user_103 = 63.9 ★4（往返 0） | 重新生成示例：每条回复唯一 tweet_id，用 in_reply_to 连链；新增导入校验（重复 tweet_id、共用 post_id、缺 in_reply_to） | 97.8 ★5，靠的是 12 轮真实往返；校验警告见 14.0 |

其他顺带的改动：
- 数据模型加了 `tweet_id`、`in_reply_to_status_id`、`parent_kind`、`post_created_at`、`first_observed_at`、`observed_baseline`，去掉了 `ts_source`。
- 生成示例时发现「正常，很多是互关来的」会被误判为问候，已记入第 7 节。
- 新增用例：问候上限生效（真实聊过 2 次 + 每天早安 → 39.9 ★2），作为待校准的取舍记录下来。
